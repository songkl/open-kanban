## 1. Background & Goal

`opencode acp` starts an ACP (Agent Client Protocol) server speaking
JSON-RPC 2.0 over stdio. From the help text the agent exposes:

```
opencode acp
start ACP (Agent Client Protocol) server

Options:
  --print-logs            print logs to stderr
  --log-level             DEBUG | INFO | WARN | ERROR
  --pure                  run without external plugins
  --port, --hostname      bind a server endpoint (0 = stdio only)
  --mdns, --mdns-domain   mDNS service discovery
  --cors                  additional CORS origins
  --cwd                   working directory
```

The goal of this analysis is to document:

1. How the CLI runner starts a *specific* agent in ACP mode.
2. How the runner drives an *interactive* task turn end-to-end.
3. How the *process and result* of the interaction are recorded today,
   what is missing, and what would be needed to close the gap.

`s-1235` already shipped the runner-side client
(`cli/src/runner/acp.ts`), so most of this report describes the
existing implementation rather than greenfield design.

## 3. How to Start a Specific Agent in ACP Mode

### 3.1 Operator-facing configuration

The operator picks the agent with `agent.bin` / `agent.binPath` and the
mode via `agent.promptMode`. The minimum config is:

```yaml
agents:
  - id: opencode-acp
    bin: opencode
    promptMode: acp
    args: []
    # acpFlag: "--acp"   # implicit; override only if the agent differs
```

The runner builds argv as `<agent.bin> … <agent.args> --acp` (or the
override flag). Stdio is forced into `pipe / pipe / pipe` so the JSON-RPC
client owns all three channels. `cwd` is taken from the per-task claim
context, falling back to the runner's own cwd.

For agents that use a different opt-in flag (the man page calls out
`claude --acp` and `gemini --acp` as standard, but some forks use
`--agent-client-protocol`), override `agent.acpFlag` rather than baking
the flag into `agent.args`.

### 3.2 Spawn wiring

`ChildProcessSpawner.spawn()` short-circuits to `spawnAcpAgent()` for
ACP mode (`cli/src/runner/spawn.ts:833`). The shell-out looks like:

```ts
spawnAcpAgent({
  bin: prepared.bin,
  args: prepared.args,             // already includes acpFlag
  cwd: prepared.cwd,
  env: prepared.env,
  timeoutMs: cfg.timeoutMs ?? 1_800_000,
  prompt: opts.prompt,
  cancelSignal: ac.signal,
});
```

`spawnAcpAgent()` itself opens the child with `stdio: ["pipe", "pipe",
"pipe"]` and constructs `new AcpClient({ transport, cwd, … })`. The
child is *not* killed by exit-code alone — the loop calls
`acpClient.cancel(sessionId)` on SIGTERM to give the agent a chance to
flush a clean `stopReason: "cancelled"` notification before the
underlying child is reaped.

### 3.3 Targeting a specific agent per task

The runner picks the agent config by matching `task.agentType` against
`agents[].id` (the same mechanism used by every other prompt mode).
Per-task overrides live in `task.agentPrompt` and `task.agentId` on the
backend model; no ACP-specific routing is required at the moment.

## 4. How an Interactive Task Turn Is Driven

### 4.1 Protocol lifecycle

`AcpClient.run(prompt)` runs three requests back-to-back:

```
1. initialize            →  handshake, protocol version, capabilities
2. session/new (cwd)     →  opens session, returns sessionId
3. session/prompt        →  drives the user turn; collects streamed
                            session/update notifications until the
                            agent returns the prompt response
```

All three frames travel as line-delimited JSON-RPC objects on the
child's stdin (one JSON object per line, terminated by `\n`). Responses
and notifications arrive on stdout; logs are free to flow on stderr.

### 4.2 Notification handling

Today only one notification shape is consumed — every other notification
type is logged through the `error` sink but otherwise ignored:

```ts
// cli/src/runner/acp.ts:548-564
this.rpc.onNotification(ACP_NOTIFICATION_UPDATE, (params) => {
  const update = params.update as Record<string, unknown> | undefined;
  if (!update) return;
  const sessionUpdate = update.sessionUpdate;
  if (sessionUpdate !== "agent_message_chunk") return;
  const content = update.content as Record<string, unknown> | undefined;
  if (!content || content.type !== "text") return;
  const text = content.text;
  if (typeof text === "string" && text.length > 0) {
    captureStdout(text);
  }
});
```

The contract per the canonical ACP spec
(agentclientprotocol.com/protocol/v1):

| `sessionUpdate` | Currently captured? |
|-----------------|---------------------|
| `user_message_chunk` | No (replayed only on `session/load`) |
| `agent_message_chunk` | **Yes — concatenated into `result.stdout`** |
| `agent_thought_chunk` | No |
| `plan` | No |
| `tool_call` (initial) | No |
| `tool_call_update` | No |
| `usage_update` | No |
| `session_info_update` | No |
| `available_commands_update` | No |

### 4.3 Cancellation

Closing the child's stdin is treated as the universal abort signal.
`spawnAcpAgent()` also fires a `session/cancel` JSON-RPC notification so
the agent can write a clean `stopReason: "cancelled"` response instead
of simply dropping the channel. The in-flight `session/prompt` Promise
then resolves with whatever text chunks were already captured, and the
spawn layer maps the exit to `reason: "signal"`.

### 4.4 Timeout / byte caps

- Wall-clock timeout: `agent.timeoutMs ?? 1_800_000` (30 min).
- Stdout byte cap: `STDOUT_TRUNCATE_BYTES` (64 KiB), shared with the
  non-ACP paths. Truncation appends a `\n[truncated]` marker so
  downstream consumers can detect it.

## 5. How the Interaction Is Recorded Today

### 5.1 What survives the run

After a successful `session/prompt` round-trip the runner forwards the
result to `POST /api/v1/runs/:taskId/finish`:

| Backend column | Populated by | Source |
|----------------|--------------|--------|
| `output` | `result.stdout` | Concatenated `agent_message_chunk` text |
| `error` | `result.stderr` | Stderr text *or* the JSON-RPC failure string |
| `exit_code` | `result.exitCode` | Always `0` on a clean ACP round-trip |
| `finished_at` | server clock | Stamp at finish |

On success, `FinishRun` invokes `CompleteTask` which advances the
underlying task to the next column and emits the completion event. The
`output` value is then surfaced on the task detail page (see s-1185)
as the agent's reply.

### 5.2 What does *not* survive

The current shape of the persisted record is intentionally minimal —
it answers "what did the agent say" but not "what did the agent do":

- **No per-tool-call trace.** The `tool_call` /
  `tool_call_update` notifications are dropped on the floor. An
  operator looking at the task detail page sees the *reply* but not
  the list of files read, commands executed, or diffs produced.
- **No plan timeline.** `sessionUpdate: "plan"` notifications
  (priority + status per entry) are ignored, so the agent's plan
  is invisible post-mortem.
- **No usage telemetry.** `usage_update` notifications (cumulative
  tokens / cost) are discarded. Cost is therefore only knowable
  through the upstream provider's billing dashboard.
- **No permission audit trail.** `session/request_permission`
  requests are answered automatically by the agent's default
  permission system because the runner doesn't subscribe; there is
  no record of which actions were auto-approved.
- **No structured transcript.** `output` is a single VARCHAR blob
  — the chronological interleaving of messages, tool calls, and
  updates is collapsed into a flat string.

### 5.3 Where the loss happens

The drop is in **one place**: the `onNotification` callback inside
`AcpClient.run()` only forwards `agent_message_chunk` text. To retain
the rest we need either:

1. A parallel handler that buffers all notification types into a
   structured transcript object, **and** a backend column or
   attachment endpoint that persists it.
2. A separate log sink (file under `logs/<taskId>-<sessionId>.ndjson`)
   that captures every frame verbatim, leaving the in-DB record as
   it is today.

Option 2 is significantly cheaper to ship and matches the pattern the
runner already uses for `logs/runTask.log`.

## 6. Gap Analysis & Recommendations

### 6.1 Minimal change (recommended for next iteration)

Persist the full JSON-RPC transcript to disk and surface a link to it
from the task detail page.

- Add `agent.sessionLog` to the runner config — when set, write every
  request/response/notification frame as NDJSON to that directory.
- The runner already emits one file per task under `logs/`; reuse
  `logs/<taskId>-<sessionId>.ndjson` rather than introducing a new
  config knob unless a per-task override is required.
- Frontend reads the transcript via a new
  `GET /api/v1/runs/:taskId/transcript` endpoint that streams the
  NDJSON and lets the UI render it as a collapsible timeline.

Estimated effort: 1 backend endpoint + 1 frontend component + ~40 lines
in `acp.ts` to forward every notification into the log sink.

### 6.2 Richer change (future)

Promote the transcript into a first-class structured record:

- New table `task_run_events` keyed by `(task_id, seq)` with columns
  for `kind` (`message` / `tool_call` / `plan` / `usage` / …), `payload`
  (JSON), `created_at`.
- New `runner/events` ingest endpoint that the CLI calls as frames
  arrive, so the UI can stream updates live during a long turn
  (instead of waiting for the prompt response).
- Schema covers the full ACP `SessionUpdate` union, including
  `tool_call_update` lifecycle (`pending` → `in_progress` →
  `completed` / `failed`) so each tool call is a row, not a blob.

Estimated effort: 1 new table + 1 endpoint + the runner-side buffering
described in 6.1. Larger surface area, so worth parking behind a
`--record-transcript` flag while the data shape stabilises.

### 6.3 Non-recommendations

- **Switching the wire format** to embed the full transcript inside
  `result.stdout` would couple the persisted record to the agent's
  text reply and break the existing task detail page. Keep the two
  channels (text reply vs. structured transcript) separate.
- **Parsing `output` retroactively** to extract tool calls is fragile
  and locks us into the agent's current chunking behaviour. The
  transcript should be written *as the frames arrive* — anything else
  is reconstructive guesswork.

---

## 7. Conclusion

The CLI already ships a complete ACP client (`s-1235`); this report is
therefore closer to a state-of-the-system doc than a design proposal.
The interactive flow — initialize → session/new → session/prompt with
cancellation and timeout — is in production and covered by tests.

The recording surface, however, is intentionally minimal: only the
streamed agent text is persisted (via `output`, s-1185). Tool calls,
plans, usage updates, and permission requests are dropped on the
floor inside the single `onNotification` callback. Closing that gap
is a separate, well-scoped piece of work (recommended path: NDJSON
transcript on disk + streaming endpoint), and the natural follow-up
ticket is a "structured transcript" sub-task under `s-1285`.
