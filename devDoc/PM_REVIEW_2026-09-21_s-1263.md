### P0-2. Column status pills still leak raw enum status values (`todo`, `in_progress`, `review`, `done`) into fully-localised pages

- Files: `frontend/src/components/ColumnCard.tsx:79`,
  `frontend/src/i18n/locales/{en,zh}.json`.
- Reproduced on `13-admin-board-light.png` and `26-admin-columns.png`
  against the **fresh** build (post-s-1262):
  ```
  Backlog      todo        #1
  In progress  in_progress #2
  Review       review      #3
  Shipped      done        #4
  ```
  Every other label on the page is in Chinese. The four status
  pills are English enum strings.
- Why this is **still here**: the code at `ColumnCard.tsx:79` reads:
  ```tsx
  t('settings.activities.details.statusLabel.${column.status}',
    { defaultValue: column.status })
  ```
  but the i18n keys were mis-placed when s-1260 added them. Both
  locale files have them at the **wrong path**:
  ```jsonc
  // en.json / zh.json
  "settings": {
    "activities": {
      // …44 activity-action keys, no "details" sub-object
    },
    "details": {                      // ← sibling, not child of activities
      "statusLabel": { "todo": "待办", "in_progress": "进行中", … },
      "statusFromTo": "状态: {{from}} → {{to}}",
      "positionFromTo": "位置: {{from}} → {{to}}",
      …
    }
  }
  ```
  Direct evidence:
  ```
  $ jq '.settings.details.statusLabel' frontend/src/i18n/locales/en.json
  { "todo": "Backlog", "in_progress": "In Progress", …, "done": "Done" }
  $ jq '.settings.activities.details'  frontend/src/i18n/locales/en.json
  null
  ```
  With the key path mismatch, `t('settings.activities.details.statusLabel.todo')`
  returns the literal key (or hits `defaultValue`), so the raw enum
  renders.
- This is the **same** finding flagged in s-1257 (P2-7) and s-1258
  (P2-7) and s-1261 (P0-1). Three reviews in a row. The s-1262
  commit message noted "P0-1 / P0-2 column-status / activity-details
  i18n keys: already shipped in s-1260 (verified en.json:968-974 and
  zh.json:968-974); the reviewer's i18n half-fix claim is stale." —
  but the keys *are* at lines 975-981, the path is the bug.
- Impact: the entire `/board/:id` page — the first thing a paying
  user lands on — has four colored status pills in the column
  headers that leak raw enums.
- Fix (≈ 6 lines + 0 JSON edits, just move keys):
  ```diff
   // Move the "details" sub-object from settings.details to settings.activities.details
   // (or: change the consumers to use settings.details.statusLabel)
  ```
  Either move the keys or change `ColumnCard.tsx:79` /
  `activityDetails.ts:26-75` / `activityDetails.test.ts:16-23` to
  read from `settings.details.*`. Whichever lands first, the
  consumers must agree.

### P0-3. The activity feed `details` field still shows the raw enum shape (`Status: 'in_progress' → 'review'`)

  `localizeActivityDetails` parser in `activityDetails.ts:37,40,42,

  t('settings.activities.details.statusFromTo', { from, to })

  `状态: 进行中 → 审核` (Chinese) or `Status: In progress → Review`
  (English) instead of `状态: 'in_progress' → 'review'`.

## P1 — Should Fix This Milestone

### P1-1. `GET /api/v1/runs/:taskId` does NOT apply `stripAnsi` / `redactRunOutputHosts` — legacy rows still leak `\u001b[0m` and LAN hosts on the live task-run endpoint

- File: `backend/internal/handlers/tasks_run.go:705` (`GetRun`),
  contrast with line 879-895 (`ListRunsHistory` *does* strip).
- Reproduced via `curl`:
  ```
  $ curl -b "kanban-token=…" http://localhost:8080/api/v1/runs/T-1001 \
        | jq -r '.run.error'
  \u001b[0m
  > build · deepseek-v4-flash
  \u001b[0m
  \u001b[0m$ \u001b[0mdate "+%Y-%m-%d" > run.log && cat run.log
  2026-09-20
  \u001b[0m
  ```
  The `output` field is clean (no ANSI), but the `error` field still
  starts with `\u001b[0m`. The board view calls this endpoint on
  every card paint, so every time an admin opens a task with a
  legacy run they see the escape literal in the modal.
- Contrast with `/runs/history` which the s-1260 fix correctly
  sanitised at read-side (`tasks_run.go:879-895`). The `GetRun`
  endpoint was missed.
- Impact: a developer opening DevTools to debug the run modal sees
  the raw escape sequence (a screen reader announces "left-bracket
  zero m"), and a future compliance audit reads the un-sanitised
  audit row.
- Fix (3-line diff in `GetRun`):
  ```go
  // Before c.JSON, mirror ListRunsHistory's read-side strip:
  run.Error = ptr(strings.TrimSpace(*run.Error)) // plus stripAnsi + redact
  run.Output = ptr(strings.TrimSpace(*run.Output))
  ```
  Or extract the strip pair into a helper and call it from both
  handlers. Plus a regression test that asserts the new shape.

### P1-2. `GET /api/v1/activities` (the permission audit log endpoint) returns `{"activities": null, …}` instead of `{"activities": [], …}` when there are no permission-audit rows

- File: `backend/internal/handlers/auth_activity.go:158, 566`
  (both `GetActivities` and `GetPermissionActivities`).
- Reproduced via `curl` (admin, no permission-audit rows in the DB):
  ```
  $ curl -b "kanban-token=…" http://localhost:8080/api/v1/activities
  {"activities":null,"hasMore":false,"total":0}
  ```
  The sibling `/api/v1/auth/activities` correctly returns
  `{"activities":[…], "hasMore":false, "total":10}`.
- Both handlers declare `var activities []Activity` and append into
  it; an empty result is `nil`, which JSON-serialises as `null`.
  CLAUDE.md says:
  > Prefer returning empty arrays `[]` over `null` for list responses.
- The dual-route design (one at `/activities`, one at
  `/auth/activities`) is also confusing — but the immediate
  contract violation is the `null` leak. s-1258's P2-1 / P2-2 fixed
  the same shape on `/api/v1/templates` and `/api/v1/archived`;
  `/api/v1/activities` was missed.
- Impact: a CLI user `curl | jq '.activities | length'` gets a jq
  error because `.activities` is `null`, not `[]`. A small but
  embarrassing regression next to two other list endpoints that
  *do* return `[]`.
- Fix (2-line diff in each handler): after the append loop,
  ```go
  if activities == nil { activities = []Activity{} }
  c.JSON(http.StatusOK, gin.H{"activities": activities, …})
  ```
  Plus a handler unit test that asserts the empty-shape contract.

### P2-3. `POST /api/v1/tasks/:id/complete` advances by ONE column, not to "Review" — verb semantics refined

- File: `backend/internal/handlers/tasks_special.go`
  (`CompleteTask` handler).
- Reproduced via `curl`:
  ```
  $ # T-1002 was in Backlog (06cc35cb…)
  $ curl -X POST ... /api/v1/tasks/T-1002/complete | jq '.columnId'
  "48a055abcec431763583e8e65434db47"   # = In progress, not Review
  $ # T-1001 was in Review (f31723…)
  $ curl -X POST ... /api/v1/tasks/T-1001/complete | jq '.columnId'
  "41e219cc5f1d5cbc1175d5279a690466"   # = Shipped, not Review
  ```
  So "complete" advances by exactly ONE column regardless of the
  source. From Backlog → In progress; from Review → Shipped.
- The s-1261 finding (P2-4) was that "complete" moves to Review;
  the actual behaviour is one-column-forward. Refined: it's not
  "wrong target" but "wrong verb" — "complete" should land the
  task in the `done` column (Shipped), not advance one slot.
- This is the same finding as s-1258 P2-5 / s-1261 P2-4. Two
  reviews in a row. s-1262 did not touch the handler.
- Fix: rename the endpoint to `POST /tasks/:id/advance` (current
  behaviour — advance one column) and reserve `POST /tasks/:id/complete`
  for "move to the column with `status = done`" semantics. Or add
  a `?target=advance|shipped` query param. 5-line diff + handler
  unit test for both modes.
