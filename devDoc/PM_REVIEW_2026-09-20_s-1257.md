## P0 — Ship Blockers

### P0-1. `settings.activities.DEVICE_APPROVE` and 6 sibling OAuth action keys leak raw i18n keys into the activity feed
- Files: `frontend/src/components/settings/ActivitiesSettings.tsx:152`,
  `frontend/src/components/ActivityTicker.tsx:87-90`.
- Reproduced as admin (`23-admin-activities.png`):
  ```
  settings.activities.DEVICE_APPROVE - kanban-client-53d958b0b5c3f677d22c6a9423278f9a
    device_code approved for client=kanban-client-…
  ```
- The `t('settings.activities.${activity.action}')` lookup returns the
  literal key string when the action is not in the `settings.activities`
  table, and the fallback guard is wrong:
  ```tsx
  typeof t(`settings.activities.${activity.action}`) === 'string'
    ? t(`settings.activities.${activity.action}`)
    : activity.action
  ```
  `typeof string === 'string'` is always `true`, so the fallback never
  fires and the raw key leaks through.
- Confirmed the action enum:
  `sqlite3 release/kanban.db "SELECT DISTINCT action FROM activities;"`
  returns `BOARD_CREATE`, `CREATE_TASK`, `DEVICE_APPROVE` — and the
  backend migrations (`backend/internal/database/migrations/sqlite/*`)
  register `DEVICE_APPROVE`, `DEVICE_CODE`, `DEVICE_CREATE`,
  `OAUTH_CLIENT_REGISTER`, `OAUTH_CLIENT_DELETE`, `OAUTH_PROVIDER_*`,
  `WEBHOOK_CREATE`, `WEBHOOK_DELETE`, `WEBHOOK_TEST`, `WEBHOOK_ROTATE`,
  and `BULK_PERMISSION_GRANT` — none of which are present in
  `frontend/src/i18n/locales/{en,zh}.json` under `settings.activities`.
- The same bug pattern ships in `ActivityTicker.tsx:87-90`, so the
  bottom-of-screen ticker will leak the same keys to every page.
- Fix (two parts):
  1. Replace the broken guard with i18next's built-in missing-key
     detection:
     ```ts
     const label = i18n.exists(`settings.activities.${activity.action}`)
       ? t(`settings.activities.${activity.action}`)
       : humanizeAction(activity.action);
     ```
     where `humanizeAction` turns `DEVICE_APPROVE` → `"Device approve"`.
     Centralise `humanizeAction` in `frontend/src/utils/activityActions.ts`
     so both `ActivitiesSettings` and `ActivityTicker` share it.
  2. Add the missing translations to both `en.json` and `zh.json`:
     ```
     "DEVICE_APPROVE":        "Device approved"        / "批准设备"
     "DEVICE_CODE":           "Device code issued"     / "签发设备码"
     "DEVICE_CREATE":         "Agent created"          / "创建 Agent"
     "OAUTH_CLIENT_REGISTER": "OAuth client registered"/ "注册 OAuth 客户端"
     "OAUTH_CLIENT_DELETE":   "OAuth client deleted"   / "删除 OAuth 客户端"
     "OAUTH_PROVIDER_CREATE": "OAuth provider added"   / "添加 OAuth 提供方"
     "OAUTH_PROVIDER_UPDATE": "OAuth provider updated" / "更新 OAuth 提供方"
     "OAUTH_PROVIDER_DELETE": "OAuth provider removed" / "删除 OAuth 提供方"
     "WEBHOOK_CREATE":        "Webhook created"        / "创建 Webhook"
     "WEBHOOK_UPDATE":        "Webhook updated"        / "更新 Webhook"
     "WEBHOOK_DELETE":        "Webhook deleted"        / "删除 Webhook"
     "WEBHOOK_TEST":          "Webhook tested"         / "测试 Webhook"
     "WEBHOOK_ROTATE":        "Webhook secret rotated" / "轮换 Webhook 密钥"
     "BULK_PERMISSION_GRANT": "Bulk permission grant"  / "批量授权"
     ```
  Estimated 80 lines across two JSON files + a 12-line utility.

### P0-3. The `kanban` CLI's default `--api-url` is `http://192.168.0.102:8080` (carry-over from a previous LAN dev box)
- File: `cli/src/program.ts` (default in `Option` declaration).
- Reproduced:
  ```
  $ kanban --help | grep api-url
    --api-url <url>  Kanban API base URL (default:
                     "http://192.168.0.102:8080")
  $ echo "boards list\nexit" | kanban shell
  kanban> Boards  http://192.168.0.102:8080
  ┌────────┬────────┬──────────────────────┐
  │ id     │ name   │ createdAt            │
  ├────────┼────────┼──────────────────────┤
  │ sys    │ sys    │ 2026-09-05T12:17:59Z │
  │ public │ public │ 2026-09-05T12:26:04Z │
  └────────┴────────┴──────────────────────┘
  ```
  The shell returns two boards (`sys`, `public`) that **don't exist in
  this release's `kanban.db`** — they're on a previous developer's LAN
  server at `192.168.0.102`. An operator who installs the CLI and
  never sets `KANBAN_API_URL` will silently target that LAN host and
  see confusing connection errors (or worse, read someone else's data).
- This is exactly the **same finding** flagged in s-1241 (P1-7) and
  re-confirmed in s-1243 (P1-7). The merge wave since then has not
  touched `cli/src/program.ts`. Repeating it here as P0 because the
  impact is "first-run data leak" if the installer's local network
  resolves the LAN IP to any box that happens to be listening.
- Fix:
  ```ts
  // cli/src/program.ts
  .option('--api-url <url>', 'Kanban API base URL',
          process.env.KANBAN_API_URL ?? process.env.OPEN_KANBAN_URL ?? 'http://localhost:8080')
  ```
  Mirror the same change in the `shell` command so the
  `auto-probing auth status on entry` line also uses the env var.
  Estimated 4-line diff.

### P1-1. The compact `TaskRunIndicator` on `TaskCard` still reads "已完成" for terminal runs in the **Review** column — looks identical to the column status
- File: `frontend/src/components/TaskRunIndicator.tsx:130` →

          ✅ 已完成 · 运行器: miniMac 16秒

  badge is identical to the "已完成" status a user would read on a
  card in the **Shipped** column. A user opening the board sees a
  "Review" column full of "已完成" labels and assumes the column
  means "all done, move them out".
- This is the **same finding** flagged in s-1243 (P1-9) and still
  present in s-1257. The merge wave touched `TaskRunIndicator.tsx`
  (added the `compact` mode and the `isLiveRun` filter) but did not
  rename the terminal-status badge.
- Fix: rename the run-status translation in `taskModal.runStatus.*`
  from `"completed": "已完成"` to `"completed": "上次运行 · 已完成"`
  / `"Last run · done"` (and the `released` / `failed` siblings to
  `"上次运行 · 排队中"` / `"上次运行 · 失败"`). Estimated 4-line
  diff in both locales.

### P1-2. `GET /api/v1/runs/:taskId` returns 404 for any task that has not been claimed, and the SPA logs a red `Failed to load resource: 404` on every page that touches a task
- File: `frontend/src/services/api.ts:984`
  (`runsApi.getByTask`).
- Reproduced via `curl`:
  ```
  $ curl -b kanban-token=… http://localhost:8080/api/v1/runs/T-9999
  {"error":"Task not found"}        HTTP 404
  ```
  The endpoint correctly returns 404, but the SPA calls it from
  every task card on first paint. With two tasks in the Review
  column we get two 404s; with four tasks across four columns we
  get four 404s on `/board/:id` paint. They appear in the browser
  console as red error lines (`getByTask … 404`) even though the UI
  correctly falls back to no badge.
- Same finding as s-1243 P1-2. The merge wave added a few more
  callsites (the new `TaskRunIndicator.compact` footer) so the
  red-error count is up.
- Fix: at `services/api.ts:991`, change the 404 path to log a
  single `console.debug` and not throw, AND/OR change the backend
  handler in `backend/internal/handlers/runs.go` to return
  `{ "run": null, "hasRun": false }` (200) when no run exists.
  Estimated 3-line diff on either side.

### P1-3. `GET /api/v1/runs/history` rows leak ANSI escape sequences into the `error` field
- File: `backend/internal/handlers/tasks_run.go:181` (the runner
  finish path) OR `backend/internal/handlers/runs.go` (the read
  side).
- Reproduced:
  ```
  $ curl -b kanban-token=… http://localhost:8080/api/v1/runs/history | jq '.[] | .error' | head -1
  "\u001b[0m\n> build · deepseek-v4-flash\n\u001b[0m$ \u001b[0mdate \"+%Y-%m-%d\" > run.log && cat run.log\n2026-09-20\n\u001b[0m\n"
  ```
  Every history row's `error` field starts with the literal
  `[0m\n> build · …\n[0m`. The CLI prints it inside a table cell;
  the activity feed surfaces it as a tooltip. A user reading the
  feed sees `\u001b[0m` rendered as raw text.
- Same finding as s-1243 P2-2. The merge wave did not address it.
- Fix: `regexp.MustCompile("\x1b\\[[0-9;]*[a-zA-Z]")` stripper in
  the runner-finish handler before persisting, OR a sanitiser in
  the read-side handler. Five-line diff in
  `backend/internal/handlers/tasks_run.go`.

### P1-4. `BoardCard` still ships a public-board lock emoji 🔒 next to the title — the icon is misread as "private" by users
- File: `frontend/src/components/BoardCard.tsx:23-26`.
- Reproduced (`11-admin-boards-light.png`):
  ```
  Product iteration 🔒
  ID: ed9d3d12a0d309d94fd4a871ad1569d6
  ```

  users a lock means "private / restricted", but the underlying

- Fix: switch the icon to 🔗 (link) or 🌍 (globe) when `isPublic`,
  and remove it entirely when the board is private. Single-line
  diff.
