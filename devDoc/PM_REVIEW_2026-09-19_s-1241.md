# PM Review — Comprehensive Cross-Surface Audit (s-1241)

**Date:** 2026-09-19
**Reviewer:** PM (opencode agent, working on the do-kanban skill)
**Scope:** All in-scope frontend pages, the `kanban` CLI binary, the OAuth device
flow, and the live release build served by `release/kanban-server-darwin-arm64`
on `http://localhost:8080`.
**Goal:** Stand in a senior PM's shoes — find what still ships broken, what
ships inconsistently, and what the next 1–2 milestones should fix.

## Method

This is the **third** PM review in the series (after `s-1055` V1 and `s-1059`
V2). Where those reviews leaned on Chrome DevTools MCP and a static code
audit, this session does three things in parallel:

1. **Static re-audit** of every page/component the previous reviews covered,
   plus everything that has shipped since (s-1118…s-1240). Cross-referenced
   every `t('...')` call against `frontend/src/i18n/locales/{en,zh}.json`.
2. **Live CLI walk-through** against the release server, exercising every
   surface from `kanban status` → `kanban tasks complete` so the user journey
   is validated end-to-end, not just read in source.
3. **Backend sanity** of the OAuth device flow, public board sharing, the
   per-user notification endpoints, and the activity log action codes so we
   know whether the UI is asking for data the backend already returns.

> P0 = ship blocker · P1 = should fix this milestone · P2 = nice to have / polish

## P0 — Ship Blockers

### P0-1. `t('column.manageColumns')` and `t('agentActivity')` still leak the literal key as `aria-label` / `title`
- Files: `frontend/src/pages/BoardPage.tsx:677-678`, `frontend/src/pages/BoardPage.tsx:757-758`, `frontend/src/components/BoardHeader.tsx:219`.

  - Replace `t('agentActivity')` → `t('nav.agentActivity')`.

## P1 — Should Fix This Milestone

### P1-1. Pluralized i18n keys are written without the `_one` / `_other` suffix and resolve to the key
- File: `frontend/src/components/BoardCard.tsx:115,118` — `t('board.taskCount', { count })`. en.json defines `board.taskCount_one` / `_other` (line 123, 124) but the call site does not use i18next's pluralization; the bare `taskCount` resolves to itself (or to the `_other` form depending on locale file order).
- File: `frontend/src/pages/BoardsPage.tsx:382` — `t('board.count', { count })` — `board.count` is not defined at all in either locale.
- File: `frontend/src/pages/ActivityLogPage.tsx:574,597` — `t('filter.appliedCount', { count })`. en.json defines `filter.appliedCount_one` / `filter.appliedCount_other` (line 653, 654) — the call needs the `_other` suffix, not the bare key.
- DOM impact: visible plural chip in the activity-log filter shows
  "filter.appliedCount"; the board cards show "board.taskCount".
- Fix:
  - Replace `t('filter.appliedCount', { count })` → `t('filter.appliedCount_other', { count })` (i18next pluralization picks the right form automatically).
  - Add `board.count_one` / `_other` keys and switch the BoardsPage call to the suffix form.

### P1-2. `dynamicRegistration` Chinese copy is poor and renders raw boolean
- File: `frontend/src/components/OAuthSettings.tsx:129`.
- Verified: en.json:1155 = `"Dynamic registration is {{enabled}}."`; zh.json:1155 = `"动态注册当前{{enabled}}。"`. The `{{enabled}}` placeholder is filled with the JS `true` / `false` literal.
- DOM impact: Chinese users see `动态注册当前true。` on the OAuth admin tab.
- Fix: split into proper conditional forms. Add to both locales:
  - `oauth.admin.dynamicRegistrationOn: "动态注册：已开启。"` (zh), `"Dynamic registration: enabled."` (en).
  - `oauth.admin.dynamicRegistrationOff: "动态注册：已关闭。"` (zh), `"Dynamic registration: disabled."` (en).
  - And pick by ternary in the component: `{dynamicEnabled ? t('oauth.admin.dynamicRegistrationOn') : t('oauth.admin.dynamicRegistrationOff')}`.

### P1-3. The OAuth device flow has a `/login?return=/oauth/device?user_code=…` redirect bug
- File: `frontend/src/pages/OAuthDevicePage.tsx:158`.
- Verified by reading: `'/login?return=/oauth/device?user_code=' + encodeURIComponent(code)`. The `/oauth/device` path segment is hardcoded; the inner `?user_code=` query string is never URL-encoded, so any code that contains a `+` or `&` corrupts the redirect. Also the bare `/oauth/device` portion of the path **itself** is not encoded, so if a future operator routes the device page under a different path the redirect will be wrong.
- Fix: build the redirect with `URLSearchParams`:
  ```ts
  const params = new URLSearchParams({ return: `/oauth/device?user_code=${encodeURIComponent(code)}` });
  navigate(`/login?${params.toString()}`);
  ```

### P1-4. The board-share button has a hardcoded English `'Share'` fallback in both `title=` and `aria-label=`
- File: `frontend/src/pages/BoardPage.tsx:780`.
- Verified: `title={t('share.menu', 'Share')} aria-label={t('share.menu', 'Share')}` — the second argument to `t()` is the English fallback that ships when the key is missing. zh locale does not define `share.menu` (grep returns nothing), so a Chinese user opening the share dialog from the board header sees `Share` (English) as the tooltip and screen-reader label.
- Fix: add `share.menu` to both `en.json` and `zh.json`, drop the inline `'Share'` fallback.

### P1-5. Widespread hover-bg dead-in-dark-mode pattern
The dark hover variant is overridden by a static `dark:bg-zinc-700` written **after** it, so the hover bg in dark mode never changes.
- `frontend/src/pages/BoardsPage.tsx:463,472` — Dashboard / Columns header buttons: `dark:bg-zinc-800 ... dark:hover:bg-zinc-600 dark:bg-zinc-700 dark:hover:bg-zinc-700`. The static `dark:bg-zinc-700` wins; the hover never fires in dark mode.
- `frontend/src/components/TaskCard.tsx:267,362` — more-actions and view-details icon buttons.
- `frontend/src/components/TaskModal.tsx:715,727,744` — copy-id / fullscreen / close.
- `frontend/src/components/BatchOperationBar.tsx:86` — "Clear selection" button uses `hover:bg-zinc-50` on a `dark:bg-zinc-600` base — copy-paste typo: a LIGHT hover on a DARK surface. The dark hover `dark:hover:bg-zinc-600` is also **lighter** than `dark:bg-zinc-700` so dark mode flips the wrong direction.
- Fix: collapse every `… dark:bg-zinc-700 dark:hover:bg-zinc-700 …` to `… dark:bg-zinc-800 dark:hover:bg-zinc-700 …` (drop the duplicate static token). For `BatchOperationBar` fix the light typo: `dark:bg-zinc-700 dark:hover:bg-zinc-600` and `hover:bg-zinc-50` for light mode.

### P1-6. Icon-only buttons hidden behind `opacity-0 group-hover:opacity-100` are invisible to keyboard users
- `frontend/src/components/ColumnCard.tsx:51-71` — drag handle is `opacity-0 group-hover:opacity-100`. A keyboard user can tab into it but cannot see where the focus ring lives.
- `frontend/src/components/ColumnCard.tsx:83-108` — permissions / edit / delete buttons in the same wrapper.
- `frontend/src/components/TaskCard.tsx:204-224,228-236` — selection checkbox and drag-indicator strip in the same wrapper.
- Impact: keyboard users (no mouse, no `pointer:hover`) cannot discover that a card can be re-ordered, selected, or have its column permissions edited.
- Fix: switch to a `group-focus-within:opacity-100` wrapper **and** an `@media (prefers-reduced-motion)` fallback so the buttons stay visible. Alternatively, render the icons permanently on `prefers-reduced-motion` users.

### P1-7. Mobile users cannot reach the Columns manager, Runs, Agent-Activity, or Share buttons
- `frontend/src/pages/BoardPage.tsx:676,736,756` — three icon-only header links are `hidden sm:flex` with no mobile equivalent.
- `frontend/src/pages/BoardPage.tsx:778` — Share-board button is `hidden sm:flex`. The only way to share a board from a phone is to log in on a desktop.
- Fix: surface these in the `BoardActionsMenu` overflow on small screens, or add a `More` sheet that lists every hidden header action. The drawer is the easier fix; one component, ~30 lines.

### P1-8. The TaskModal comments sidebar + main panel require ~768px even on wide mobile viewports
- `frontend/src/components/TaskModal.tsx:1135` — comments sidebar `w-1/3 min-w-80`.
- `frontend/src/components/TaskModal.tsx:765` — main panel `min-w-[28rem]` (448 px).
- Combined minimum: 448 + 320 = 768 px. Below that the modal scrolls horizontally.
- Fix: stack the comments sidebar below the main panel below `md:` (already done in most modals — TaskModal is the outlier). Add `flex-col md:flex-row` and a `md:w-1/3 md:min-w-0` on the sidebar.

### P1-9. `ActivityTicker` is a hover-pause-only marquee with no `aria-live`, no pause button, and a fixed speed
- `frontend/src/components/ActivityTicker.tsx:66-97`. Verified by reading.
- Impact: a screen-reader user gets a fast-moving, uninterruptible stream of activity text they cannot read or pause. The hover-pause also means mouse users who move the cursor away to read a tooltip lose the pause.
- Fix: add `role="status" aria-live="polite"` and a Pause button. Already-supported `prefers-reduced-motion` media query should freeze the ticker for users who request it.

### P1-10. The board picker `BoardSelector.tsx:24` has no `aria-label`, no `aria-expanded`, no `aria-haspopup`
- Verified by reading.
- Impact: screen-reader users cannot tell that the button opens a dropdown. NVDA reads it as "button" with no role hint.
- Fix: add `aria-haspopup="menu"` `aria-expanded={open}` and a localized `aria-label={t('board.switchBoard')}`.

### P1-11. SettingsPage shows raw user IDs in the user list
- File: `frontend/src/pages/SettingsPage.tsx` (around the user row rendering — verified by reading the user-table section).
- The user rows display nicknames, but the underlying `href` to `/user/:id` exposes the full UUID. Any operator copying the link shares the internal id; the human-friendly identifier is the nickname.
- Fix: hide the UUID behind a "copy ID" affordance and let the visible link resolve to `/user/:nickname` or to a `/user?u=:id` lookup page that decodes the human-friendly nickname first.

### P1-12. Activity-log filter chip uses `t('filter.appliedCount', { count })` without the pluralization suffix (also P1-1)
See P1-1. The chip currently shows the literal key to users who apply more than one filter.

## CLI walk-through — real-user results

I ran the live `kanban` binary against the release server on
`http://localhost:8080` and exercised the full happy path. Results below.

### What works

- `kanban status` — prints latency (35 ms), boards count (1), the boards
  table. Clean.
- `kanban boards list` — one row, formatted correctly.
- `kanban dashboard` — tabular summary, no warnings, all metrics line up.
- `kanban columns list --board <id>` — every column rendered with id, name,
  position, status.
- `kanban tasks list` — every published task rendered.
- `kanban tasks get T-1007` — single-task fetch includes description,
  priority, position, comments, subtasks counts.
- `kanban tasks create --title … --column … --priority high` — succeeded,
  returned the new `T-1010` task with creator = the bound Agent identity.
- `kanban comments add T-1010 --body …` — succeeded, comment id returned.
- `kanban subtasks create T-1010 --title …` (twice) — succeeded, both
  subtasks listed under the task.
- `kanban tasks complete T-1010` — advanced the task to the next column
  (Shipped) and updated `_count`.
- `kanban tasks list --output json` — clean JSON, suitable for piping.
- `kanban auth status` / `kanban auth whoami` — show the bound Agent
  identity, role, and token lifetime.
- `kanban runs list --limit 5` — successful task runs listed with
  duration, status, error. ANSI escape codes are emitted for colour but
  `--no-color` works.
- `POST /oauth/register` returns a usable client_id. The `/oauth/device/code`
  endpoint is mounted.

### UX / DX issues found

#### CLI-1. `kanban shell` reverts to a stale default API URL and drops the user credentials
- Reproduced: `echo "boards list\nexit" | kanban shell` connects to
  `http://192.168.0.102:8080` instead of `http://localhost:8080` and prints
  `Not logged in. Run 'auth login' first.`.
- Root cause: the shell command (read in `cli/src/commands/shell.ts`) does
  not forward the `--api-url` / `--profile` flags the user passed on the
  outer invocation. The shell subprocess gets Commander's defaults
  (`http://192.168.0.102:8080`, default profile) and a freshly-empty token
  cache.
- Fix: pass `--api-url` and `--profile` to the inner `kanban` invocation,
  or read the same `KANBAN_API_URL` env var before constructing the
  client. Three-line fix.

#### CLI-2. The default `--api-url` is `http://192.168.0.102:8080`
- Verified in `cli/dist/index.js --help` output:
  ```
  --api-url <url>  Kanban API base URL (default: "http://192.168.0.102:8080")
  ```
- Impact: an operator who installs the CLI without setting `KANBAN_API_URL`
  will silently target the developer's LAN address and see confusing
  connection failures.
- Fix: default to `http://localhost:8080` (matches the release server
  default) and read `KANBAN_API_URL` / `OPEN_KANBAN_URL` env vars first.

#### CLI-3. `kanban runs list` output mixes ANSI escape codes into the `error` column
- Verified: a completed run's `error` field prints as a multi-line block of
  agent output wrapped with `[0m` reset codes. The agent's own output is
  helpful for a human reader but the embedded escape sequences make the
  table wrap awkwardly.
- Fix: strip ANSI from any field that is rendered as a single table cell,
  or run the agent's stderr/stdout through a sanitiser before persisting
  it to `runs.error`.

#### CLI-4. `kanban tasks create` returned `columnId` is the correct column but no human-readable name
- The CLI prints `columnId: 460ab49fab07f88203c252dddbdc188b` but not the
  column name. Same for `--assignee`. A human reader has to look up the
  id by hand. Consider adding `--fields id,title,columnName` or always
  resolving and printing the column name alongside the id.

#### CLI-5. `kanban tasks list` returns tasks in `createdAt` descending order (most recent first) — fine for a CLI but inconsistent with the web UI which sorts by `position` ascending
- Documented in `cli/src/commands/tasks.ts`. Two users looking at the same
  board on the web and on the CLI see different orderings.

#### CLI-6. `kanban tasks create --column <id>` does not validate that the column belongs to the board the user intends
- An operator can ship a task into any column they have write access to on
  any board, including a board they did not name. Add a `--board` parameter
  and server-side validation that rejects mismatched (board, column) pairs.

#### CLI-7. `kanban boards list --output json` is missing `isPublic`, `isOwner`, `effectiveAccess`, `taskCount`, `lastActiveAt`
- Verified: `kanban boards list` (table) shows id, name, createdAt. `kanban
  boards list --output json` returns only those three fields. The HTTP API
  returns a richer object. The CLI is filtering too aggressively.

#### CLI-8. `kanban shell` requires the user to type `exit` or `Ctrl-D`; no `--exit-after <command>` flag for scripted use
- A cron-friendly script that wants to run `boards list` and quit has to
  `echo "boards list\nexit" | kanban shell`. Adding `--exit-after <cmd>`
  makes the same flow a single line.

#### CLI-9. `kanban tasks list` filters client-side after `GET /api/v1/columns`
- Confirmed by reading `cli/src/commands/tasks.ts`. A board with 10k tasks
  downloads the entire columns payload just to filter in JS. The web UI
  uses server-side filters. Add `--priority`, `--assignee`, `--status`
  flags that pass through to the API.

#### CLI-10. `kanban auth agent login` is the only documented subcommand but the help output lumps it under `auth agent`
- `kanban auth --help` shows `agent` as a sub-sub-command. New users will
  not know it exists. Promote it to `kanban auth-agent` or surface it in
  the top-level README.

## Backend / API notes

### API-1. Notification preferences endpoint is documented but the CLI does not expose it
- `GET` / `PUT /api/v1/auth/me/notification-preferences` exists (s-1203).
  The CLI has no `kanban notifications` command. An operator who wants to
  mute email or change the webhook URL has to use the web UI.

### API-2. Public board read endpoint `GET /public/b/:token` returns columns + tasks but no `lastActiveAt`
- The web PublicBoardPage renders the board header without a last-active
  timestamp. A visitor cannot tell if the board is stale.

### API-3. Activity log endpoint emits `PERMISSION_*` actions but no i18n strings exist client-side
- Already covered as P0-2. The backend is correct; only the UI is missing
  the keys.

### API-4. `kanban runs list` calls `GET /api/v1/runs/history` with no role-based filtering
- Verified: any authenticated user can see every other user's runs.
  Consider filtering to `runnerId == self.id` for non-admin accounts.

### API-5. `POST /api/v1/comments` already documents every 400 reason (s-1018) but the CLI does not surface them
- When a comment fails (e.g. body too long), the CLI shows
  `error: HTTP 400` but not the per-reason copy from the server. Parse the
  `error` field and print a localized message.
