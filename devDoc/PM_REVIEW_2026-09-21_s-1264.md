### P0-1. Column status pills still leak raw enum status values into a fully-localised page (FIFTH review in a row)

- Files: `frontend/src/components/ColumnCard.tsx:79`,
  `frontend/src/i18n/locales/{en,zh}.json` (lines 920 + 966 in `en.json`).
- Reproduced on `13-admin-board-light.png`, `14-admin-board-dark.png`,

  search placeholder, dark toggle, etc.) is in Chinese. The four status
  pills in the column header are English enum strings.
- Reproduced on the dark-mode board (`14-admin-board-dark.png`):
  ```
  Backlog      todo        1
  In progress  in_progress 0
  Review       review      2
  Shipped      done        0
  ```
  Same defect, dimmer.
- Reproduced on `/columns` (`26-admin-columns.png`) — the entire 列管理
  page reads Chinese except for the four status pills on each row:
  ```
  Backlog      todo        #1
  In progress  in_progress #2
  Review       review      #3
  Shipped      done        #4
  ```
- Reproduced on mobile (`41-mobile-board.png`) — the Backlog column
  header still reads `todo` even though the column chip at the top
  reads `Backlog`.
- Why this is **still here**: the code at `ColumnCard.tsx:79` reads:
  ```tsx
  t('settings.activities.details.statusLabel.${column.status}',
    { defaultValue: column.status })
  ```
  but the i18n keys are mis-placed. Both locale files have them at
  the wrong path:
  ```jsonc
  // en.json
  920: "activities": { … },        // ← 44 activity keys, NO "details" here
  966: "details": {                // ← sibling of activities, not child
  975:   "statusLabel": { "todo": "Backlog", "in_progress": "In Progress", …, "done": "Done" },
  976:   "statusFromTo": "Status: {{from}} → {{to}}",
  …
  ```
  Direct evidence:
  ```
  $ jq '.settings.details.statusLabel' frontend/src/i18n/locales/en.json
  { "todo": "Backlog", "in_progress": "In Progress", …, "done": "Done" }
  $ jq '.settings.activities.details'  frontend/src/i18n/locales/en.json
  null
  ```
  With the dotted-key path mismatch, `t('settings.activities.details.statusLabel.todo')`
  returns the literal key (or hits the `defaultValue`), so the raw
  enum renders.
- This is the same finding flagged in **s-1257 P2-7, s-1258 P2-7,
  s-1261 P0-1, s-1263 P0-2**. Four reviews in a row. The s-1262
  commit message explicitly noted "P0-1 / P0-2 column-status /
  activity-details i18n keys: already shipped in s-1260" — but the
  keys have never actually been moved to the consumer's expected
  path.
- Impact: the entire `/board/:id` page — the first thing a paying
  user lands on — and the `/columns` manager page both have
  English enum pills in the column headers. A board with 10 columns
  (a common PM scenario) renders 10 English pills.
- Fix (≈ 6 lines + 0 JSON edits):
  - **Option A** (cheapest): change the 4 consumers
    (`ColumnCard.tsx:79`, `activityDetails.ts:37,40,42`, and any
    other `t('settings.activities.details.*')` call) to read from
    `settings.details.*`. Run `TestActivityDetails` to verify the
    parser still finds the keys.
  - **Option B**: move the `details` sub-object from
    `settings.details` to `settings.activities.details` in both
    locale files. Either move works as long as consumers + JSON
    agree.

### P1-1. `GET /api/v1/activities` still returns `{"activities": null, …}` instead of `[]` (s-1263 P1-2 carryover)

- File: `backend/internal/handlers/auth_activity.go:158, 566`
  (both `GetActivities` and `GetPermissionActivities`).
- Reproduced via `curl` (admin, no permission-audit rows in the DB):
  ```
  $ curl -b "kanban-token=…" http://localhost:8084/api/v1/activities
  {"activities":null,"hasMore":false,"total":0}
  ```
  The sibling `/api/v1/auth/activities` correctly returns
  `{"activities":[…], "hasMore":false, "total":10}`.
- Both handlers declare `var activities []Activity` and append into
  it; an empty result is `nil`, which JSON-serialises as `null`.
  CLAUDE.md says: "Prefer returning empty arrays `[]` over `null`
  for list responses."
- s-1258's P2-1 / P2-2 fixed the same shape on `/api/v1/templates`
  and `/api/v1/archived`; `/api/v1/activities` was missed both
  times.
- Impact: a CLI user `curl … /activities | jq '.activities | length'`
  gets `null` and a jq error. A future i18n string like "5 records"
  breaks when the count is `null`.
- Fix (2-line diff in each handler): after the append loop,
  ```go
  if activities == nil { activities = []Activity{} }
  c.JSON(http.StatusOK, gin.H{"activities": activities, …})
  ```
  Plus a handler unit test that asserts the empty-shape contract.

### P1-2. Anonymous visitor still gets four 401s from `/api/v1/auth/me` on every first paint (s-1263 P2-2 carryover)

  error: Failed to load resource: the server responded with a status of 401 (Unauthorized)
  error: Failed to load resource: the server responded with a status of 401 (Unauthorized)

### P2-3. `dashboard.stats.topAgentsByActivity` is computed from `activities` table rows, not from agent heartbeats — the result is usually empty (NEW minor finding)

- File: `backend/internal/handlers/dashboard.go:107-125` (`GetDashboardStats`).
- Reproduced:
  ```
  $ curl … /api/v1/dashboard/stats | jq '.topAgentsByActivity'
  []
  ```
  The agent exists (`/api/v1/auth/activities?agentOnly=true` shows
  Iteration Bot), the agent page (`19-admin-agent-activity.png`) shows
  Iteration Bot was last active 7 hours ago, but the dashboard
  ranking is *empty*.
- Why: the SQL at line 107-116 joins `users` to `activities`,
  filters by `u.type = 'AGENT'` AND `a.created_at >= datetime('now', '-7 days')`,
  and orders by `COUNT(a.id)`. An agent that has never *acted*
  (created a task, ran a runner, etc.) — only heartbeated —
  contributes zero rows and is invisible.
- Impact: the dashboard's "Agent 活跃度排行" card is permanently
