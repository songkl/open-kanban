# PM Review — Senior PM walkthrough (s-1243)

**Date:** 2026-09-19
**Reviewer:** PM (opencode agent, working on the do-kanban skill)
**Scope:** End-to-end product walkthrough of the live release build
served by `release/kanban-server-darwin-arm64` on `http://localhost:8080`,
plus the freshly built `cli/dist/index.js`. The previous PM review
(`s-1241` → `s-1242`) shipped a wide net of fixes; this session is the
**fourth** in the series and looks for what *still* leaks, what *broke*,
and what *still hurts a paying user* on first contact.

## Method

1. **CLI walk-through** — `cli/dist/index.js` against the live server, both
   with `--api-url` and with the default URL. Confirmed which `s-1241`
   findings were closed by `s-1242` and which were not.
2. **Admin + subadmin browser walkthrough** — Playwright against the
   release build, 70+ screenshots in `devDoc/pm-review-s1243-shots/`.
   Logged in as both `admin` (ADMIN role, fresh token) and `subadmin`
   (MEMBER role) so admin-gated UI could be reached.
3. **Source re-audit** — `git diff 7bbb254..HEAD -- "frontend/src/**"` to
   cross-check every `t('…')` call, every `dark:bg-*` token, and every
   `opacity-0 group-hover:opacity-100` block against the live DOM.
4. **Backend smoke** — direct curl against `/api/v1/*` to confirm what the
   server actually returns vs. what the frontend expects.

## P0 — Ship Blockers

### P0-1. `t('column.selectAll')` still leaks the literal key on every board page (light + dark, desktop + mobile)
- File: `frontend/src/components/Column.tsx:249, 274`.
- Verified in the live DOM:
  ```
  <label class="sr-only" for="select-all-<id>">column.selectAll</label>
  <span role="checkbox" aria-label="column.selectAll">
  ```
- The `column.selectAll` key does not exist in `frontend/src/i18n/locales/zh.json`
  under the `column` block. The closest entry is
  `common.selectAll` / `column.selectAll` at line 28 (a *top-level*
  duplicate that's also being misused). The two visible-to-screen-reader
  `aria-label`s on every column's "select all" checkbox therefore read
  `column.selectAll` to assistive tech.
- Fix: add `column.selectAll: "Select all"` / `"全选"` (zh) to both
  locales under the `column` namespace, or change the call to
  `t('common.selectAll')`. One-line diff. Same regression in V2.

### P0-2. `BoardCard` trash button `title` / `aria-label` resolves to the **deletion confirmation message**, not the button label
- File: `frontend/src/components/BoardCard.tsx:206-207` (introduced by
  s-1242).
- The s-1242 commit added:
  ```tsx
  title={t('board.deleteBoard')}
  aria-label={t('board.deleteBoard')}
  ```
  But `board.deleteBoard` is defined as the *confirmation message*
  ("确定要删除看板 \"{{name}}\" 吗？…" / "Are you sure you want to
  delete board \"{{name}}\"? …"). Hovering or focusing the trash
  button therefore shows the confirmation copy with an empty `{{name}}`
  placeholder; screen readers read the same thing.
- Fix: replace with `t('board.deleteBoardTitle')`, which already exists
  in both locales (`zh.json:581`, `en.json:581`). One-token diff.

### P0-3. `ColumnCard` action buttons (权限 / 编辑 / 删除) still ship only light variants on dark mode
- File: `frontend/src/components/ColumnCard.tsx:83-108`.
- Verified in dark mode by hovering the column row as admin:
  `devDoc/pm-review-s1243-shots/41-columns-hover-dark.png`. The
  权限 / 编辑 / 删除 chips render with `bg-violet-50 text-violet-600` /
  `bg-blue-50 text-blue-600` / `bg-red-50 text-red-600` — pure pastels
  on `bg-zinc-800`. They look like misplaced stickers.
- This was flagged as **P0-4 (V2)** in `s-1059`, again in the s-1241
  review's "What was actually fixed" list as resolved, but the source
  still has zero `dark:` variants on those three buttons.
- Fix:
  ```tsx
  bg-violet-50 dark:bg-violet-900/30 text-violet-600 dark:text-violet-300
  bg-blue-50   dark:bg-blue-900/30   text-blue-600   dark:text-blue-300
  bg-red-50    dark:bg-red-900/30    text-red-600    dark:text-red-300
  ```
  Estimated 6-line diff. Single PR.

### P0-4. `/board/public` (the slug `public`) loads the logged-in user's first board, not a public board
- Verified: `curl -s http://localhost:8080/board/public` (no auth) shows
  the public Product-iteration board's content because the SPA falls
  back through `HomePage` and the boards list. With auth, navigating to
  `/board/public` resolves to whatever `boardsApi.getAll()` returns
  first (currently `Product iteration`), not the board named `public`
  (which is in the `default` server DB but not in `release/kanban.db`).
- Impact: a user clicking a shared deep-link like `/board/public` ends
  up on the wrong board with no explanation. Worse: a viewer who only
  has READ on `Product iteration` thinks they were granted access to
  the `public` board.
- Fix: either remove the `/board/public` route from the navbar /
  bookmarks, or rename the slug to `p/:token` (the actual public-share
  contract from s-1204) and treat `public` as an invalid id.

## P1 — Should Fix This Milestone

### P1-1. `BoardCard` shows the same "{{count}} 个任务" string in both the meta label and the value cell
- File: `frontend/src/components/BoardCard.tsx:115, 118`. The label
  cell renders `t('board.taskCount_other', { count: 0 })` and the value
  cell renders the same `t('board.taskCount_other', { count: taskCount })`.
- Visible result on `Product iteration`:
  ```
  TASK COUNT
  0 个任务              ← label
  6 个任务              ← value
  ```
  See `devDoc/pm-review-s1243-shots/01-boards.png` — the label and value
  both literally say "X 个任务". A user reads it as a duplicated metric.
- Fix: keep the plural form on the value cell only; replace the label
  with a static `t('board.taskCountLabel')` ("任务" / "Tasks") or
  remove the label cell entirely.

### P1-2. `/api/v1/runs/:taskId` returns 404 for every task that has not been claimed by a runner, and the browser logs it as a console error
- File: `frontend/src/services/api.ts:984` (`runsApi.getByTask`).
- Verified across `devDoc/pm-review-s1243-shots/02-board-sys.png`:
  ```
  GET /api/v1/runs/T-1010 → 404 Run not found
  GET /api/v1/runs/T-1011 → 404 Run not found
  ```
  Both 404s appear in DevTools' red error list even though the
  frontend correctly normalises them to `null` (`api.ts:991`). Operators
  chasing "what's wrong with my board" find the noise distracting.
- Fix: either make the API return `{ "run": null, "hasRun": false }` on
  the empty case (200), or set the response status to 204 No Content.
  Three-line diff. Alternatively, treat 404 the same as `null` and add
  `Cache-Control: max-age=5, must-revalidate` so the browser stops
  re-fetching after navigation.

### P1-3. `/user/:userId` silently redirects to `/settings?tab=users` when the URL contains a nickname instead of a UUID
- Files: `frontend/src/pages/UserDetailPage.tsx:57-60`,
  `frontend/src/App.tsx:89`.
- Reproduced as admin (`devDoc/pm-review-s1243-shots/82-user-detail-light.png`):
  visiting `/user/subadmin` immediately navigates away to the user list
  because the page does `usersData.find((u) => u.id === userId)` and
  `userId` is `subadmin` not a UUID.
- This is a regression of the s-1059 / s-1241 P2-1 finding ("/user/:userId
  route does not exist in the published build"). The route is now wired
  but the lookup contract still expects the UUID.
- Fix: at `UserDetailPage.tsx:57`, fall back to `usersData.find((u) =>
  u.nickname === userId)` and add a banner when the route was
  nickname-resolved. Or, change the link convention on `SettingsPage`
  to `/user?u=:id` (query param) so the router can do the lookup
  unambiguously.

### P1-4. The mobile TaskModal "编辑任务" button collapses into a vertical pill on narrow viewports
- File: `frontend/src/components/TaskModal.tsx:228` (header bar
  `flex-wrap`).
- Reproduced at 375 px (`devDoc/pm-review-s1243-shots/63-mobile-task-modal.png`):
  the wide Chinese label "编辑任务" (4 chars × button width) is wrapped
  character-by-character into a vertical block, so the modal header
  shows a 100-px-tall "pill" with the four characters stacked. On a
  phone, the modal occupies the full screen so this becomes a top-bug.
- Fix: shrink to `text-xs` on `< sm:`, or move the button to a separate
  row above the metadata block. Three-line diff.

### P1-5. `BoardCard` and the action menu ship a 1-px `border-zinc-200/40` ring on dark mode cards (BoardCard.tsx:53, BatchOperationBar.tsx:42)
- Verified: `devDoc/pm-review-s1243-shots/23-dark-boards.png`. The dark
  card uses `border border-zinc-100 dark:border-zinc-700` — fine. The
  adjacent `BatchOperationBar` ring is `ring-1 ring-zinc-200/20
  dark:ring-zinc-600/50` which mixes light `/20` and dark `/50` opacity
  scales; on the dark card the ring is brighter than the card body,
  drawing the eye to the bar's left edge with no functional reason.
- Fix: pick a single scale (recommend `ring-1 ring-zinc-700/40` in dark
  and `ring-zinc-200` in light). One-line diff.

### P1-6. `kanban shell` still drops the user's `--api-url` and `--profile` on entry (s-1241 CLI-1)
- Reproduced:
  ```
  $ echo "boards list\nexit" | kanban shell           # default URL 192.168.0.102:8080
  $ echo "boards list\nexit" | kanban shell --api-url http://localhost:8080
       Profile:    (default)            ← still default
       Host:       http://192.168.0.102:8080  ← still default URL
       Not logged in. Run `auth login` first.
  ```
- The s-1242 commit log does not mention `cli/src/commands/shell.ts`.
  The shell still rebuilds a Commander program without re-injecting
  `--api-url` / `--profile`, and the token cache is dropped on the
  child process boundary.

### P1-7. The CLI's default `--api-url` is `http://192.168.0.102:8080` (s-1241 CLI-2)
- Reproduced:
  ```
  $ kanban status
  Kanban API        http://192.168.0.102:8080
  Status            online
  Boards           2
  ```
  The "default" LAN address from a previous developer's box. An
  operator who installs the CLI without setting `KANBAN_API_URL` /
  `OPEN_KANBAN_URL` will target that LAN host and see confusing
  connection failures (or worse, a third-party server they did not
  authorise). The `program.ts` default is not overridden anywhere.
- Fix: change `cli/src/program.ts` default to `http://localhost:8080`
  and read `KANBAN_API_URL` / `OPEN_KANBAN_URL` env vars first.

### P1-8. The CLI's `tasks complete` and `runs list` commands refuse to run after a single successful device-flow login
- Reproduced immediately after a successful `kanban auth login` (cookie
  authenticated as `Iteration Bot`):
  ```
  $ kanban tasks complete T-1011
  Not logged in. Run 'auth login' first.
  failed to refresh access token: no refresh token available
  ```
  Same for `kanban runs list`.
- Root cause: the device flow on the admin user returned an OAuth
  identity with no refresh token. `cli/src/auth/commands.ts:401-410`
  writes the access token but then on every subsequent call, the
  runner's token cache hits the "refresh token missing" branch and the
  cached access token is treated as invalid.
- Fix: persist the long-lived `kanban-token` value (the `kanban-token`
  cookie that the device flow also writes) as a fallback identity. Or
  document that the device flow with `--as-human` does not yield a
  refreshable token. The s-1241 review called this out as `API-4` /
  `CLI-10`.

### P1-9. The `kanban-board-sys` page TaskCard claims a runner in "已完成" (completed) state when the runner's task run row has finished
- File: `frontend/src/components/TaskCard.tsx` (badge near `runnerId`).
- Visible on `devDoc/pm-review-s1243-shots/02-board-sys.png`:
  ```
  T-1007 使用 cli
  已完成 · 运行器: local-mac  8秒
  ```
  T-1007 is in the **Review** column. The "已完成" badge reads as "this
  task is done" even though the task has not been advanced. The badge
  means "the last run finished", but the wording is identical to the
  column status text.
- Fix: rename to "最近运行 · 完成" / "Last run · done" (en) and
  "上次运行 · 已完成" (zh) so the two states are visually distinct.
  Or: surface the same status enum as a colored chip instead of a full
  sentence.

## P2 — Nice to Have / Polish

### P2-1. `kanban tasks create` still prints `columnId` as the bare UUID, with no human-readable name
- Reproduced: `kanban tasks create --title "x" --column <id>` returns a
  `columnId` field but no column name. Same for `--assignee`.
- s-1241 CLI-4 still applies.

### P2-2. `/api/v1/runs/history` rows leak ANSI escape sequences into the `error` field
- Verified by `curl -b "kanban-token=…" http://localhost:8080/api/v1/runs/history`:
  every row's `error` value starts with the literal string `[0m\n> build · MiniMax-M3\n[0m`.
  The CLI renders them inside a table cell, the web UI shows them in
  the activity row "PM Review s-1243 test → 失败" tooltip.
- Fix: strip ANSI before persisting (`backend/internal/handlers/tasks_run.go:181`,
  the runner finish path) or in the read-side handler. Five-line diff.

### P2-3. Auth pages 401-fan-out on first paint
- `frontend/src/services/api.ts:135` redirects to `/login` on 401
  unconditionally. Every authenticated page on cold load fires 4-6
  parallel requests before the cookie is verified, then a subset of
  them 401 (notifications, templates, auth/agents). The browser console
  shows red `Failed to load resource: 401` lines on every page.
- Fix: route the auth probe through a centralised store (Zustand or
  React Query) so the first request decides and subsequent calls wait
  for the result. Same finding as s-1241 P1-5 / V2-2.

### P2-4. `/api/v1/templates` returns 401 for any non-admin viewer, even for users who only need public template metadata
- Verified: `GET /api/v1/templates` (no auth) returns `[]` (empty), but
  `GET /api/v1/templates` (subadmin) returns 401. The endpoint should
  at least return the public marketplace templates without auth so the
  marketplace page is reachable to logged-out users (s-1204 promise).
- Fix: align the route handler with `GET /api/v1/public/templates`.

### P2-5. The PublicBoard share link exists (`/public/b/:token`) but the navbar still says "分享" only on the board header, not on the boards page
- The s-1204 public-share feature shipped in `frontend/src/pages/PublicBoardPage.tsx`
  but the boards list cards have no "copy share link" affordance. An
  admin who wants to share a board with a guest has to navigate into
  the board, hover the Share button, copy the URL, then share it
  manually.
- Fix: surface "Share" on each `BoardCard` via a small icon button when
  `board.isPublic` is true. Five-line diff.

### P2-6. The "暂无任务 / 点击添加新任务" empty-column state is hard to spot in dark mode
- `frontend/src/components/Column.tsx` (around the empty state).
- `devDoc/pm-review-s1243-shots/24-dark-board-sys.png` shows the
  In progress column with `暂无任务` / `您没有在该列添加任务的权限` in a
  dim grey that nearly disappears on `bg-zinc-900`.
- Fix: bump text to `dark:text-zinc-300` and surface a "+" CTA pill in
  the centre (same as light mode).

### P2-7. The board header truncates `Product iteration` to "Product itera..." on narrow widths
- `frontend/src/components/BoardSelector.tsx:24`. The picker pill
  shows `Product itera...` at 1440 × 900 when 4 columns of action
  buttons crowd the header (see `devDoc/pm-review-s1243-shots/02-board-sys.png`).
- Fix: increase the picker's `max-w` or move it to a `<details>`
  dropdown. Two-line diff.

### P2-8. `Kanban CLI` status help still documents `kanban auth-agent` indirectly but exposes only `kanban auth agent`
- `kanban auth --help` lists `agent` as a sub-sub-command (s-1241
  CLI-10 still applies). New users won't know the CLI ships an
  unattended-runner setup.

### P2-9. `/templates` (without `/marketplace`) is a no-op route in the SPA
- The router registers `/templates/marketplace` (s-1204) but no
  `/templates` fallback. A user who types `/templates` (perhaps from an
  outdated bookmark) sees a blank page. Reproduced in the early
  walkthrough (`devDoc/pm-review-s1243-shots/12-templates.png`).
- Fix: redirect `/templates` → `/templates/marketplace` (one-line
  `<Navigate>` in `App.tsx`).

### P2-10. `SettingsPage` user list shows `禁用` (Disable) buttons for every row including the admin row
- `devDoc/pm-review-s1243-shots/48-users-light.png`. The admin's row has
  a `禁用` button on the right. Clicking it would lock the operator
  out of the system. There is no "you cannot disable yourself" guard.
- Fix: in the disable handler, refuse if `targetUser.id === currentUser.id`.
