## P0 — Ship Blockers

### P0-1. `/columns` page and column status pills on `/board/:id` still leak raw enum status values (`todo`, `in_progress`, `review`, `done`) into a fully-localised Chinese page

- Files: `frontend/src/components/ColumnCard.tsx:79`,
  `frontend/src/i18n/locales/{en,zh}.json`.
- Reproduced as admin (`26-admin-columns.png`):
  ```
  Backlog      todo        #1
  In progress  in_progress #2
  Review       review      #3
  Shipped      done        #4
  ```
  And on the live board (`13-admin-board-light.png`,
  `14-admin-board-dark.png`, `41-mobile-board.png`) — the four
  column headers each carry a coloured pill with the raw enum.
- Why this is **still here**: s-1259 added a new
  `ColumnCard.tsx:79` template:
  ```tsx
  {t(`settings.activities.details.statusLabel.${column.status}`,
     { defaultValue: column.status })}
  ```
  but the matching i18n keys were **never added**. Both locale
  files have an empty `settings.activities.details.statusLabel`
  object (verified by reading the JSON directly), so the
  `defaultValue` wins and the raw enum is what the user sees.
- This is the **same** finding flagged in s-1257 (P2-7) and
  s-1258 (P2-7). Two reviews in a row. The s-1259 PR introduced
  the wrong "i18n half-fix" — the column card is now
  i18n-aware in shape but still leaks the raw enum because the
  keys are missing.
- Impact: the entire `/board/:id` page is the first thing a
  paying user lands on. Every column header carries a
  `todo` / `in_progress` / `review` / `done` pill that breaks the
  localised chrome around it. The /columns management page is
  even worse — every other label on the page is Chinese.
- Fix (≈12 lines + JSON keys):
  ```ts
  // ColumnCard.tsx already uses t(... defaultValue: ...).
  // Just add the keys:
  // settings.activities.details.statusLabel.todo        = "待办" / "Backlog"
  // settings.activities.details.statusLabel.in_progress = "进行中" / "In progress"
  // settings.activities.details.statusLabel.review     = "审核" / "Review"
  // settings.activities.details.statusLabel.done        = "已完成" / "Shipped"
  ```
  in both `en.json` and `zh.json`.

### P0-2. The activity feed `details` field still shows the raw Chinese / English enum shape (`状态: 'in_progress' → 'review'`) instead of a localised sentence

- Files: `frontend/src/utils/activityDetails.ts`,
  `frontend/src/i18n/locales/{en,zh}.json`.
- Reproduced as admin (`18-admin-activities.png`):
  ```
  更新任务 - Add OAuth provider settings page
      状态: 'in_progress' → 'review'
  更新任务 - Add OAuth provider settings page
      状态: 'todo' → 'in_progress'
  更新任务 - Document the activity i18n key map
      状态: 'in_progress' → 'review'
  ```
  Every UPDATE_TASK row's `details` field is the raw enum literal.
- Why this is **still here**: s-1260 introduced a new
  `localizeActivityDetails` parser that *would* translate the row
  — but, like P0-1, the i18n keys it needs
  (`settings.activities.details.statusLabel.{todo,in_progress,review,done}`
  + `settings.activities.details.statusFromTo` +
  `settings.activities.details.positionFromTo` +
  `settings.activities.details.reordered`) were **never added**.
  The parser's own fallback rule (line 48) detects this and
  returns `null`, so the UI ends up rendering the raw `details`
  value instead of crashing with a dotted-key leak. The
  "translation is wired up but the dictionary is empty"
  pattern is identical to P0-1 above.
- This is the **same** finding flagged in s-1258 (P1-2). One
  review in a row. The s-1260 PR added the parser but not the
  keys.
- Impact: the activity log is the audit trail every operator
  reads when chasing "who moved this card yesterday". Today it
  mixes the raw English sentence from `services.UpdateTask` with
  the raw Chinese sentence from `services.CreateTask`, both
  unreadable for the average user.
- Fix: same shape as P0-1 — populate the dictionary. Then verify
  the parser succeeds by running the board move flow and
  confirming the row reads `状态: 进行中 → 审核` instead of
  `状态: 'in_progress' → 'review'`.

### P0-3. `POST /api/v1/tasks` defaults to `published: false` (i.e. *draft*), and `kanban tasks create` silently hides this from the operator

- File: `backend/internal/handlers/tasks.go` (the `CreateTask`
  handler).
- Reproduced via curl:
  ```
  $ curl -X POST … /api/v1/tasks -d '{"title":"Default-published task",
         "columnId":"…","priority":"low"}'
  {"id":"T-1006","title":"Default-published task",
   "published":false,"columnId":"…", … }
  $ curl … /api/v1/columns?boardId=… | jq '.[].tasks | length'
  0
  $ curl … /api/v1/drafts | jq length
  1
  ```
  Confirmed end-to-end: `15-admin-drafts.png` shows the
  "Default-published task" sitting in the drafts box even
  though the operator never asked for a draft.
- This is the **same** finding flagged in s-1258 (P2-4). One
  review in a row. s-1260 did not touch `CreateTask`.
- Impact: every AI agent and CLI user writing
  `kanban tasks create --title "x" --column <id>` posts a draft,
  then reloads the board to see it missing, then has to call
  `kanban tasks publish <id>`. That's an entire round-trip
  added to the create flow and breaks the implicit "create → it
  appears on the board" contract.
- Fix: default `published: true` and add a `published: false`
  opt-in for the existing draft flow. 1-line handler change +
  docs update + a regression test that asserts
  `tasksApi.create({title, columnId}).published === true`.
